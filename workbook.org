* How to use this workbook
:PROPERTIES:
:VISIBILITY: children
:END:

This is a set of *tasks*, not a textbook. Each exercise hands you a concrete
thing to accomplish against real data. You will not have been told the flag,
function, or syntax you need — reaching for it (=man=, =--help=, =SPC h f=, a
guess) *is* the exercise. Only after trying should you open the folded /Hint/
and /Solution/ under each task.

Never used Emacs or Vim? Start with track 0. Everything below assumes it.
New to the command line? Track 2 starts from zero. The tracks run from the
editor and the shell, through the system itself (users, processes, git,
networking, auditing), to programming languages and their debuggers.

The bare minimum to read this file right now:
- =j= / =k= move down / up a line. =TAB= on a heading opens or closes it.
- If something looks stuck, press =ESC=, then =C-g= (hold Ctrl, press g).
- =SPC q q= quits Emacs.

Everything folds. The file opens showing only the tracks.
- =TAB= on a track  → reveals its exercises (still folded).
- =TAB= on an exercise → reveals the task, plus a folded /Hint/ and /Solution/.
- =TAB= again on /Solution/ → the answer.

Where you see a source block, run it in place with =SPC c c= (or =C-c C-c=).
It executes right here in the lab, in =/root/corpus=, and prints its output
back into the buffer under =#+RESULTS:=.

Suggested order is top to bottom: each track leans on habits from the last.
Mark progress with =C-c C-t= (cycles =TODO=/=DONE=) on any exercise heading.

The data lives in =/root/corpus= plus =/root/workbook-data=, both prepared for
you when the lab starts (see *Setup*).

* 0. Emacs & Vim fundamentals
:PROPERTIES:
:VISIBILITY: children
:END:

From zero to fluent in the editor this whole workbook lives in. This Emacs
speaks *Vim* (via Evil mode): you get Vim's fast, modal editing on top of
Emacs's Org, Babel, SLIME and help system. By the end of this track you will
move without arrow keys, edit with operators, run code blocks, drive a Lisp
REPL, and find the answer to "what does this key do?" yourself.

How keys are written:
- =C-x= means hold Ctrl and press x. =M-x= means hold Meta (Alt/Option) and
  press x. On a Mac terminal, turn on "Use Option as Meta key" (Terminal.app:
  Settings → Profiles → Keyboard; iTerm2: Left Option key → Esc+). Or press
  =ESC= and then the key: =ESC x= is the same as =M-x=.
- =SPC f f= means press space, then f, then f — one after another, not together.
- =RET= is Enter, =TAB= is Tab, =ESC= is Escape.

Your practice files live in =/root/workbook-data/practice=. Links like
[[file:/root/workbook-data/practice/motions.txt][motions.txt]] open with =C-c C-o= while the cursor is on them.

** TODO E0.1 — Modes, and how to always get out
Vim is /modal/: keys mean different things depending on the mode. Look at the
bottom line of the screen (the /mode line/): =<N>= is Normal, =<I>= Insert,
=<V>= Visual, =<E>= plain Emacs. Get into Insert mode, type your name at the
end of this line, and get back to Normal mode. Then undo it.
You'll meet: =i=, =ESC=, =u=, =C-g=, and the mode indicator.
*** Hint
Normal mode is for moving and commanding; Insert mode is for typing text. =i=
enters Insert, =ESC= always returns to Normal. =u= undoes, =C-r= redoes.
=C-g= is Emacs's universal "cancel": it aborts half-typed commands and prompts.
*** Solution
=A= (append at end of line), type your name, =ESC=, then =u=. When lost: =ESC=,
then =C-g=, and look at the mode line. Nothing in Normal mode inserts text, so
stray keypresses are rarely destructive — and =u= fixes the rest.

** TODO E0.2 — Move without arrow keys
Open [[file:/root/workbook-data/practice/motions.txt][motions.txt]] (=C-c C-o= on the link) and follow its instructions
down to the last line and back to the top, never touching an arrow key.
You'll meet: =h j k l=, =w b e=, =0 ^ $=, =gg G=, ={ }=, =C-d C-u=, counts.
*** Hint
=h j k l= are left, down, up, right. =w=/=b= hop by word, =0=/=$= line start and
end, =gg=/=G= buffer top and bottom, =}= / ={= next/previous blank line.
A number before a motion repeats it: =5j=, =3w=, =12G= (line 12).
*** Solution
Muscle memory, not a single answer. The key idea: every motion is a /noun/ you
will later combine with /verbs/ (E0.4). =zz= / =zt= / =zb= put the cursor line
in the middle / top / bottom of the screen. Back to the workbook: =SPC ,= then
pick =workbook.org=.

** TODO E0.3 — Jump, search, and come back
In motions.txt: jump to the =x= in "box" with one command, find both
=TREASURE= lines, bounce between matching brackets, then return to where you
started.
You'll meet: =f= / =t= / =;=, =/= search with =n= / =N=, =*=, =%=, =C-o=.
*** Hint
=fx= lands on the next =x= in the line; =;= repeats it. =/TREASURE RET=
searches, =n= / =N= step through hits (the counter in the mode line shows
"which of how many"). =%= on a bracket jumps to its partner. =C-o= walks back
through your jump history.
*** Solution
=fx=, then =/TREASURE RET n=, then =%= on the =(=, then =C-o= a few times.
=*= searches for the word under the cursor — the fastest way to find other uses
of a name in code.

** TODO E0.4 — Operators: the grammar of Vim
Open [[file:/root/workbook-data/practice/edit-me.txt][edit-me.txt]] and fix lines 1–12. Each line names the keys to use.
You'll meet: =d= / =c= / =y= + motion, text objects (=iw=, =i"=, =i(=), =dd=,
=p=, =r=, =J=, =.=, =gU=.
*** Hint
Vim edits are sentences: /operator/ + /motion/. =d= deletes, =c= changes
(deletes and enters Insert), =y= yanks (copies). =dw= deletes a word, =d$= to the
end of the line, =ciw= changes the word under the cursor, =ci"= everything
inside the quotes, =ci(= everything inside the parens. Doubling an operator
acts on the whole line: =dd=, =cc=, =yy=. =p= / =P= paste after / before. =.=
repeats your last change.
*** Solution
1 =dw= on the second "the" · 2 =cw fast ESC= · 3 =ci" hello ESC= ·
4 =ci( user ESC= · 5 =D= (same as =d$=) · 6 =gUiw= · 7 =r2= on the 1 ·
8–9 =ddp= on line 8 · 10–11 =J= on line 10 · 12 =yy3p=. Once an edit works,
=.= repeats it anywhere: fix one typo, jump to the next with =n=, press =.=.

** TODO E0.5 — Visual mode and block editing

You'll meet: =v=, =V=, =C-v=, =>=, block insert with =I=.
*** Hint

=I- ESC=. =gv= reselects the last selection if you need it again.

** TODO E0.7 — Search and replace

** TODO E0.8 — Files, buffers, and windows

one, and get back here.
You'll meet: =SPC .=, =SPC ,=, =SPC f r=, =SPC b k=, =SPC w v= / =SPC w s=,
=C-w= + =h j k l=, =SPC w o=, =SPC w d=.
*** Hint
A /buffer/ is an open thing (file, REPL, help page). A /window/ is a pane
showing a buffer. =SPC .= opens a file (type to narrow, =TAB= to complete a
directory, =RET= to open). =SPC ,= switches buffer. =SPC w v= splits
side-by-side; =C-w l= / =C-w h= moves right/left between windows.

=SPC o d= brings the dashboard back. Avoid =:q= to close files — in Emacs it
closes the /window/, and on the last one quits Emacs.

** TODO E0.10 — Help yourself (no C-h needed)
Find out: (a) what =SPC c c= runs, (b) what =org-babel-load-languages= is set

** TODO E0.15 — Structural editing: slurp, barf, wrap, raise
Work through [[file:/root/workbook-data/practice/parens.lisp][parens.lisp]]: all seven transformations, using only the
structural commands.
You'll meet: paredit via =SPC k s= / =S= / =b= / =B= / =w= / =W= / =r= / =j= / =J=.
*** Hint
Lisp code is a tree of lists; paredit edits the tree, never unbalancing the
parens. /Slurp/ pulls the next thing /into/ the list around the cursor; /barf/
pushes the last thing /out/. Capital letters work on the left side.
=SPC k w= wraps in new parens, =SPC k W= removes the parens around you,
=SPC k r= replaces the parent list with the thing under the cursor,
=SPC k J= / =SPC k j= split and join lists.
*** Solution
1 =SPC k s= · 2 =SPC k b= · 3 =SPC k S= · 4 =SPC k w= then =i print SPC ESC= ·
5 cursor on the =(= of =(compute)=, =SPC k r= · 6 cursor on =progn=, =SPC k W= ·
7 cursor on the space after 2, =SPC k J=; then on the space between the two
lists, =SPC k j=.
In Insert mode, typing =(= always inserts a matching =)=. If a Normal-mode
=x= or =dd= ever leaves parens unbalanced, =u= undoes it; prefer =SPC k W=
for removing parens.

* 1. tmux
:PROPERTIES:
:VISIBILITY: children
:END:

A terminal that outlives you. tmux runs /inside/ the lab and keeps your shells,
editors and REPLs alive after you close the terminal: detach, walk away, come
back with =./container-lab.sh enter NAME=, reattach, and everything is exactly
where you left it. It also splits one terminal into windows and panes, so the
editor, a shell, and a =tail -f= can sit side by side for the tracks ahead.

Every tmux command starts with the /prefix/ =C-b= (hold Ctrl, press b, let go),
then a key. So =C-b d= means "Ctrl-b, then d". The lab ships a =~/.tmux.conf=
that adds a few friendlier keys; E1.7 walks through it. From your Mac,
=./container-lab.sh attach NAME= enters a lab straight into a tmux session
called =main=, creating it if needed.

** TODO E1.1 — Sessions that survive

Then leave the lab entirely (=exit=), come back in with
=./container-lab.sh enter NAME=, and reattach: =top= should still be running.

*** Hint

*** Solution

=tmux attach -t work=. =q= quits =top=; =tmux kill-session -t work= ends the
session. =./container-lab.sh attach NAME= does the new-or-attach step for you
every time.

** TODO E1.2 — Windows: tabs for your terminal
In one session, make three windows named =edit=, =shell= and =logs=, jump
between them by number and by name, then close one.
You'll meet: =C-b c=, =C-b ,=, =C-b n= / =C-b p=, =C-b 1=…=9=, =C-b w=,
=C-b &=.

=shell=, =C-b w= lets you choose visually. Typing =exit= in a window's only

should be short, and why =sudo= is audited so heavily.

* 4. Processes & signals
:PROPERTIES:
:VISIBILITY: children
:END:

Every running program is a process with a PID, a parent, an owner, open files,
and a state. You'll learn to see them, rank them, signal them, deprioritise
them, look inside them through =/proc=, and, with =strace=, watch every request
a program makes to the kernel. That last one answers "why is this program doing
that?" when nothing else will. Helpers live in =/root/workbook-data/procs=.

** TODO E4.1 — What's running?
List every process with its owner, PID, parent PID, CPU and memory. Find PID 1
and what it is. Show your own shell's ancestry up to PID 1.
You'll meet: =ps aux=, =ps -ef=, =ps -o=, =ps --forest=, =pstree=, =$$=,
=$PPID=.
*** Hint
=ps aux= (BSD style) and =ps -ef= (System V style) both list everything.
=ps -o pid,ppid,user,stat,cmd= chooses columns. =pstree -p= draws the tree.
PID 1 is the first process the kernel starts; here it's whatever the lab's
entrypoint left running.
*** Solution
#+begin_src bash :results output

ps -eo pid,ppid,user,%cpu,%mem,cmd --sort=-%mem | head -6
pstree -ps $$
#+end_src
The =STAT= column: =R= running, =S= sleeping, =D= waiting on I/O, =T= stopped,
=Z= zombie (finished but not yet collected by its parent).

** TODO E4.2 — top and htop

*** Hint
=top= updates every few seconds; inside it =P= sorts by CPU, =M= by memory,
=k= kills a PID, =q= quits. =htop= is friendlier: arrows select, =F9= sends a
signal, =F5= shows the tree. =top -b -n 1= prints one snapshot for scripts.
*** Solution
#+begin_src bash :dir /root/workbook-data/procs :results output

#+end_src
A process at ~100% CPU is using one whole core; on 4 vCPUs the maximum is 400%.

** TODO E4.3 — Signals
Run =sleeper.sh= and send it =INT=, =HUP=, =USR1=, =STOP=, =CONT= and finally
=TERM=, predicting each reaction. Then start it again and try =KILL=: what's
different?
You'll meet: =kill -l=, =kill -SIGNAL PID=, =pkill=, =killall=, =trap=,
TERM vs KILL, =C-c= = INT, =C-z= = TSTP.
*** Hint
=kill= sends a signal, not necessarily death. =TERM= (the default) politely
asks a process to exit and can be caught; =KILL= (9) and =STOP= can never be
caught, blocked or ignored. =HUP= traditionally means "reload your config".
=sleeper.sh= uses =trap= to react to the catchable ones.
*** Solution
#+begin_src bash :dir /root/workbook-data/procs :results output

for sig in INT HUP USR1; do kill -$sig $pid; sleep 1.2; done

kill -CONT $pid; kill -TERM $pid; sleep 1.2
cat sleeper.log
./sleeper.sh > /dev/null & pid=$!; sleep 0.5; kill -KILL $pid; sleep 0.2
ps -p $pid > /dev/null || echo "gone, with no chance to clean up"
#+end_src
(=env --default-signal=INT= is only needed here because a non-interactive
shell starts background jobs with =INT= ignored; from your own prompt, plain
=./sleeper.sh &= works.) Always try =TERM= first and give the process a moment: =KILL= skips its cleanup
(temp files, flushing data, releasing locks).

** TODO E4.5 — Inside /proc

** TODO E4.6 — lsof and the case of the missing disk space
Create a 200 MB file, keep it open with a background =tail -f=, and delete it.
Did =df= report the space back? Find the culprit with =lsof=, then free the
space.
You'll meet: =lsof -p=, =lsof +L1=, =lsof -i=, =fuser=, "deleted" files.
*** Hint
Deleting a file removes its /name/; the data is only freed once no process
still has it open. =lsof +L1= lists open files with no names left. =lsof -i
:22= shows who is using port 22, =fuser -v FILE= who is using a file.
*** Solution
#+begin_src bash :dir /tmp :results output

writes to it keeps filling the disk invisibly until the service is restarted.

** TODO E4.7 — strace: the mystery program

** TODO E4.8 — strace: profiles, children, and running processes

** TODO E8.2 — Company-wide average salary

*** Hint

** TODO E8.3 — Average salary *per department*

*** Hint
=sum[$4]+=$5= and =n[$4]++= build per-dept totals. Loop the keys in =END=.
*** Solution

This four-line pattern — accumulate into an array keyed by a field, report in
END — is the single most useful thing awk does.

** TODO E8.4 — Tally HTTP status codes in the access log

*** Hint

an array keyed by =$9=.
*** Solution
#+begin_src bash

#+end_src
Compare this to the grep gymnastics in E6.3 — awk got the field for free.

** TODO E8.5 — Top 5 IPs by bytes transferred

*** Hint

*** Solution
#+begin_src bash

** TODO E8.6 — Word frequency, in awk alone
Top 15 words of any book — no grep/sort pipeline, do it inside awk.
You'll meet: =gsub=, =tolower=, =split=, and sorting an array by hand-ish.
*** Hint
Lowercase =$0= (=tolower=), turn non-letters into spaces (=gsub(/[^a-z]+/," ")=),

*** Solution
#+begin_src bash

#+end_src

*** Hint

** TODO E8.8 — A formatted salary-band report
Add a computed column: LOW (<70k), MID, HIGH (>=110k). Print a tidy table.
You'll meet: =BEGIN=, =printf= column widths, rebuilding =$0=/=OFS=.
*** Hint

** TODO E9.2 — Line/word/char counts for every book

You'll meet: =for= over a glob, capturing =wc= output, arithmetic.
*** Hint
=for f in /root/corpus/*.txt; do ... done=. =read l w c < <(wc -l -w -c < "$f")=
splits wc's three numbers. Keep running totals with =$(( ))=.
*** Solution
#+begin_src bash :dir /root

  tl=$((tl+l)); tw=$((tw+w)); tc=$((tc+c))
done
printf "%6d %6d %8d  TOTAL\n" "$tl" "$tw" "$tc"
#+end_src

** TODO E9.4 — Rename the messy files safely

  # mv -- "$f" "$new"

** TODO E9.5 — Make failure loud

** TODO E9.6 — A reusable function + a self-cleaning temp file

You'll meet: functions, =local=, =mktemp=, =trap ... EXIT=.
*** Hint

** TODO E11.2 — Compressors compared

* 14. Observability & performance
:PROPERTIES:
:VISIBILITY: children
:END:

Measure, don't guess. How long does it take and where did the time go? Where
did the memory and the disk go? Is the machine busy with CPU or waiting on the
disk? And which of two ways is actually faster? The tools here answer those
questions in seconds. =procs/hog.sh= from track 4 is handy for making load.

** TODO E14.1 — time: real, user and sys
Time =sleep 1=, a CPU-bound loop, and =find /nix/store -name '*.so' | wc -l=.
Explain the three numbers for each. Then get the peak memory of a command.
You'll meet: the =time= keyword, GNU =/usr/bin/time -v= (here
=command time -v=), real vs user vs sys, maximum resident set size.
*** Hint
/real/ is wall-clock time; /user/ is CPU time spent in the program's own code;
/sys/ is CPU time the kernel spent on its behalf (system calls, I/O). Sleeping
uses neither. A multithreaded program can have user > real. GNU time's =-v=
adds memory and I/O statistics; =command time= skips bash's built-in keyword.
*** Solution
#+begin_src bash :results output

* 15. Auditing with auditd
:PROPERTIES:
:VISIBILITY: children
:END:

The Linux audit system records security-relevant events inside the kernel:
who read or changed a file, who ran which program, which access was denied,
tied to the user who originally logged in even after =sudo=. It's how servers
answer "who changed =/etc/passwd= and when?" and it's a requirement in most
security standards. =auditctl= loads rules into the kernel, =auditd= writes
events to =/var/log/audit/audit.log=, and =ausearch= and =aureport= read them.

Each lab is its own VM with its own kernel, so experimenting here can't affect
anything else. The lab's audit config is in =/etc/audit/auditd.conf=.

** TODO E15.1 — Is auditing on?

You'll meet: =auditctl -s=, =auditctl -e 1=, =auditd -c=, =pid=,
=/var/log/audit/audit.log=.
*** Hint
=auditctl -s= shows the kernel's status: =enabled 1= means on, =pid= is the
daemon receiving events (0 means nobody). There's no service manager in a lab,
so start the daemon yourself: =auditd -c /etc/audit= (it backgrounds itself).
*** Solution
#+begin_src bash :results output
pgrep -x auditd > /dev/null || auditd -c /etc/audit
sleep 1
auditctl -e 1 > /dev/null
auditctl -s | grep -E '^(enabled|pid|backlog)'
tail -2 /var/log/audit/audit.log | cut -c1-110
#+end_src

** TODO E19.5 — Sort employees by salary with =qsort=

*** Hint

#include <stdio.h>
#include <stdlib.h>
struct Emp { int id; char first[32], last[32], dept[16]; long salary; };
static int by_salary_desc(const void *a, const void *b){
    long s = ((const struct Emp*)a)->salary, t = ((const struct Emp*)b)->salary;
    return (t > s) - (t < s);
}
int main(void){
    FILE *f = fopen("/root/corpus/employees.csv", "r");
    if (!f){ perror("fopen"); return 1; }
    char header[256]; if (!fgets(header, sizeof header, f)) return 1;  /* skip */
    struct Emp *e = NULL; size_t n = 0, cap = 0;
    struct Emp tmp;
    while (fscanf(f, "%d,%31[^,],%31[^,],%15[^,],%ld,%*s\n",
                  &tmp.id, tmp.first, tmp.last, tmp.dept, &tmp.salary) == 5) {
        if (n == cap){ cap = cap ? cap*2 : 64; e = realloc(e, cap*sizeof *e); }
        e[n++] = tmp;
    }
    fclose(f);
    qsort(e, n, sizeof *e, by_salary_desc);
    for (size_t i = 0; i < 5 && i < n; i++)
        printf("%-9s %-10s %ld\n", e[i].dept, e[i].last, e[i].salary);
    free(e);
    return 0;
}

(defun corpus-word-freq (file &optional n)

      (downcase-region (point-min) (point-max))
      (goto-char (point-min))
      (while (re-search-forward "[a-z]+" nil t)
        (let ((w (match-string 0)))
          (puthash w (1+ (gethash w counts 0)) counts))))
    (let (pairs)
      (maphash (lambda (k v) (push (cons k v) pairs)) counts)
      (setq pairs (seq-take (sort pairs (lambda (a b) (> (cdr a) (cdr b)))) n))
      (with-current-buffer (get-buffer-create "*freq*")
        (erase-buffer)
        (dolist (p pairs) (insert (format "%6d  %s\n" (cdr p) (car p))))
        (pop-to-buffer (current-buffer))))))
;; try: M-x corpus-word-freq RET /root/corpus/moby-dick.txt RET
#+end_src
Five implementations, one algorithm. That comparison — pipeline vs field-tool
vs scripting-language vs systems-language vs editor-extension — is the real
lesson of the whole workbook.

* 23. Debuggers
:PROPERTIES:
:VISIBILITY: children
:END:

Stop guessing, start looking. A debugger freezes a running program so you can
walk its call stack, read every variable, and watch the moment a value goes
wrong. You'll use five of them — gdb for C, pdb for Python, Delve for Go, the
Emacs debugger and Edebug for Elisp, and SLIME's debugger for Common Lisp — on
small programs with real bugs, then drive the same sessions from Neovim and
Emacs.

Each language has its own dialect, but the ideas are the same everywhere:
/breakpoint/ (stop here), /step/ (into a call), /next/ (over it), /finish/ or
/out/ (to the caller), /print/ (look), /backtrace/ (how did I get here?), and
/frames/ (move up and down the stack). Learn them once, use them in every
language.

The buggy programs live in =/root/workbook-data/debug=. Each exercise asks you
to find the bug with the debugger, not by reading the source — resist peeking.
Solution blocks run the debugger non-interactively so you can compare notes;
the real exercise is typing those commands yourself.
